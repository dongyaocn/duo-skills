# 架构决策记录（duo-adr）

两种模式：**起草**（新决策）与**评审**（检测既有决策与代码现状的漂移）。

## 输入

- 起草：`<决策主题一句话>`（如"溯源批次号生成策略"）
- 评审：`<ADR 编号或路径>`（如 `0001`）

## 起草模式

1. **收集上下文**：定位决策涉及的代码现状（grep/读关键文件）+ 扫描既有 ADR 目录，列出**相关决策**（本决策必须与之兼容或显式替代的）；
2. **结构化起草**（编号顺延，`docs/adr/NNNN-<slug>.md`）：

```markdown
# NNNN. <决策标题>
状态：<提出 | 接受 | 废弃（被 NNNN 替代）| 替代（NNNN）>
日期：YYYY-MM-DD

## 上下文（为什么现在要做这个决策：现状痛点/约束/触发事件）
## 决策（做什么，具体到可执行的口径；负向边界写"不做什么"）
## 后果（正面/负面/风险与缓解；含回滚触发条件）
## 备选方案（≥2 个，对比表：维度=复杂度/迁移成本/扩展性/团队熟悉度，说明为何落选）
```

3. **冲突检测**：新决策与相关既有 ADR 逐条比对——冲突时三选一并在文档显式声明：修改新决策兼容之 / 提交既有 ADR 状态改"废弃（被本篇替代）" / 报告用户裁决；
4. 用户确认状态"接受"后落盘；ADR 目录不存在时建之（含 README 索引一行）。

## 评审模式（决策漂移检测）

1. 读目标 ADR 的"决策"节，提取可验证主张（逐条列：如"批次号店内唯一约束在 DB 层"）；
2. 逐主张核对代码现状（grep/读实现）——三态：**相符 / 漂移**（代码与主张不符，列证据 file:line）/ **失效**（主张针对的代码已不存在）；
3. 产出漂移报告 + 处置建议：漂移属演化 → 起草新 ADR 替代（走起草模式）；漂移属违规 → 列入 duo-debt 台账或直接开工单纠正；
4. 不改代码，只出报告。

## 边界

- ADR 记录"为什么这么定"，不记实现细节（那属于代码与工单）；
- 起草需要的信息不足（说不清约束与痛点）时先列澄清问题，不硬写；
- 一次只处理一个决策主题；一揽子架构梳理拆多次调用。
