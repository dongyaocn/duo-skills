# 工单并行重排（duo-reschedule）

对**已存在的工单**（串行拆的、或拆完后依赖关系变化的）重新分析并行性，产出新的派工波次方案。与 duo-intake 的分工：intake 在拆单时设计并行，本 skill 对存量票回头重排。

## 输入

- `<feature>`（可选）：缺省从当前 feature 目录识别；也可直接给工单号列表（如 `05 06 07 08`）限定重排范围
- 范围默认=该 feature 全部**未 done** 工单；`done` 票是既成事实永不参与

## 流程（四步，拍板点在 3）

### 1. 现状盘点

逐张解析未完成票：

- **状态**：`claimed`（实施在飞，视为**锁定**——重排围绕它进行，不中断在飞 Codex，除非用户明确要求中止）/ `ready-for-agent` / `ready-for-human` / `needs-triage`；
- **改动面**（文件级冲突判定的数据源，按可信度排序）：① 简报"代码锚点"节（已派过工的票有）→ ② 工单范围节声明的文件/控制器/表 → ③ 编排方 grep 实际代码探测（票面提到某控制器/服务名时定位真实路径，两条票命中同一文件即记交集）；
- **既有依赖**：`Blocked by` / `协调` / `并行组` 标注。

### 2. 两两冲突分析

对范围内每对票 (A, B) 按三层并行模型判定（标准同 duo-intake 并行拆分模型）：

| 检查项 | 判定来源 | 结果 |
|---|---|---|
| L1 跨仓 | 改动面所属仓库 | 不同仓 → 可并行（契约若已冻结） |
| 文件交集 | 盒点文件集合（含迁移 SQL） | 交集非空 → 强制串行 |
| 语义依赖 | B 是否消费 A 新增/修改的接口·函数·枚举·配置键·表列 | 有 → 串行（A 先） |
| 迁移表交集 | 两票 ALTER/CREATE 的表名 | 同表 → 串行 |
| 演练数据冲突 | 断言店铺 id/数据前缀/共享表行 | 互踩 → 需先隔离设计才可并行 |

输出**冲突矩阵**（简表）+ 每对判定理由一句话。

### 3. 波次方案（拍板点）

生成重排方案给用户：

```text
## 重排方案 · <feature>（串行 N 波 → 并行 M 波，预估提速 x%）

### 冲突矩阵
| 对 | 判定 | 理由 |
| A×B | 串行（A先） | 同改 Trace.php |

### 派工波次
波次 1（并行组 G1·L2）：[A, C] —— A 已在飞，补派 C
波次 2（G1 合入后）：[B]（Blocked by A）
波次 3：[D]（独立，可提前插任意波次空档）

### 关键路径
A → B 链（Bis 瓶颈）；C/D 可全流程并行

### 风险与前置
- C 与 A 演练同店铺 → C 断言改前缀 C14-（改脚本前先派 A 无冲突部分？否——改 C 的简报数据约定）
```

要点：

1. claimed 票放进它所在波次的"已在飞"位，其余票围绕它排；
2. 每个并行组给出**合入顺序**（先基座后消费方）与 ff 失败时的受控 rebase 提示（协议见 duo-review）；
3. 提速预估口径=波次数变化（不承诺工时，Codex 实施时长不可精确预估）；
4. 给出"若想再提一档"的可行性提示（如把某串行对拆成契约冻结的前后端两票——但这属于改票范围，需用户另行决定是否走）。

### 4. 工单改写（拍板后执行）

1. 按方案更新各票 `## 依赖` 节：`并行组: <组名|无>`、`Blocked by` 调整、合入顺序注释；
2. 波次 1 中立即可派的票 `Status:` 置 `ready-for-agent`（needs-triage → ready 需用户在方案里逐张确认）；
3. 重排结果追加到 feature 目录 `.scratch/<feature>/` 下工单的 `## Comments`（一行：`2026-xx-xx 并行重排：入组 G1，波次 2`），不重写历史；
4. 提示下一步：`/duo-dispatch <NN>` 补派波次票。

## 边界

- 只重排未完成票；`done` 与其衍生的依赖已消解（原 Blocked by 已 done 的票自动解除，视为可派候选）；
- `ready-for-human` 票不进并行组（人工裁决是硬串行点）；
- 两两冲突判定拿不准（票面信息不足且 grep 无法定位）时，该对**保守判串行**并在矩阵标 `⚠ 待澄清`，不猜；
- 重排方案不改 spec 与验收标准，只动派工顺序与并行标注。
