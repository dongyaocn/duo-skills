# 方案设计沙盘（duo-design）

重大方案动手前的**结构化推演**——把"拍脑袋"变成"过清单"。产出设计文档，可直接作为 `/duo-intake` 的输入拆单。

## 输入

- `<方案主题>`（一句话）+ 可选草案/讨论记录路径
- `<粒度>`（可选）：`模块级`（默认，跨多文件的方案）/ `函数级`（单点实现方案，精简推演）

## 推演六步（模块级全走，函数级走 1/3/5）

### 1. 模块边界

- 画出改动涉及的模块/服务/表，每个标注**职责一句话**（说不清职责=边界糊，先解决这个）；
- 依赖方向箭头图（ASCII 即可）；出现双向依赖/环 → 亮红灯，先给出解环方案再继续。

### 2. 数据流

- 写路径：请求/事件 → 每步状态变化 → 落库（标注事务边界与幂等点）；
- 读路径：查询 → 数据来源 → 缓存/聚合点；
- 与既有数据流的交叉点高亮（交叉点=冲突高发区）。

### 3. 失败模式（轻量 FMEA）

每个环节回答三连：**挂了会怎样 / 能否降级继续 / 如何恢复**——

```text
| 环节 | 失败场景 | 影响 | 降级 | 恢复 |
| Redis 不可用 | 序号生成失败 | 建批次阻塞 | 回退 DB max+1 | 自愈，跨日重置 |
```

- 无降级路径的单点 → 标 `⚠ 硬单点`（要么补降级，要么写清接受的代价）；
- 恢复手段依赖人工介入的 → 记入回滚节。

### 4. 备选方案对比（≥2）

对比维度：复杂度 / 迁移成本 / 扩展性 / 团队熟悉度 / 失败半径（挂了波及多大）；落选方案保留一句话落选理由（半年后翻案时它就是起点）。

### 5. 回滚路径

- 上线后发现问题的回滚动作（代码回退/数据回退/开关降级，各自可行性）；
- **不可逆变更显式列出**（数据迁移/删列/对外契约发布），逐条给"做了就回不去"的补偿方案或明确接受。

### 6. 验证策略（衔接流水线）

- 断言接缝草案（哪些走接口演练/哪些走视觉/哪些两者都要）；
- 回归红线清单（哪些既有行为不得变）；
- 灰度/开关建议（能否分批放量）。

## 产出

`.scratch/<feature>/design-<主题>.md`（或 `docs/design/`，随项目惯例），六节对应六步。文档头部一行判定：**绿灯（可拆单）/ 黄灯（列出待决问题）/ 红灯（存在未解环/硬单点未接受）**——黄红灯先解决再进 `/duo-intake`。

## 边界

- 沙盘不改代码；与 /duo-adr 的分工：ADR 记"为什么这样定"（单向沉淀），沙盘推演"这样定行不行"（事前验证）——沙盘结论涉及长期取舍的，提炼成 ADR 落盘；
- 已有设计稿/讨论记录时先读再推演，不无视既有结论重来；
- 推演发现需求本身有洞（数据口径不清/约束互斥）→ 停下出澄清清单，不替需求方拍板。
