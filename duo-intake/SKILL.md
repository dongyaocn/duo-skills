# 需求整理与工单拆分（duo-intake）

把原始需求（口语描述/文档/设计稿/随手记）变成可派工的 spec + 工单集。产出前一切待用户拍板，拍板后才进 duo 流水线。

## 输入

- `<需求>`：任意形态——一段话、会议记录、需求文档路径、设计稿路径、issue 链接内容
- `<feature>`（可选）：指定 `.scratch/<feature>/`；缺省时从需求提炼一个 kebab-case 名并与用户确认

## 流程（四步，拍板点在 1 和 4）

### 1. 需求澄清（拍板点一）

1. 通读需求，提取：目标、涉及系统面（前后端/多仓/表结构/接口/页面）、显式约束、隐含假设；
2. **生成澄清问题清单**：模糊点、边界条件、异常路径、依赖系统、数据口径——每题给出 2-4 个候选答案并标注推荐项（拍板成本最低的问法）；一批不超过 10 题，超出则按影响面排序分批；
3. 用 AskUserQuestion（或清单交互）逐题拍板，**逐题记录确认结果与日期**（汇成"需求方确认记录"，Q 编号沿用）；
4. 需求本身自相矛盾或超出系统现状过多时，先报告矛盾点请用户裁决，不自行调和。

### 2. 生成 spec

写 `.scratch/<feature>/spec.md`，结构（六节，全部中文）：

```markdown
# <Feature 名>（一句话定位）
## 目标与背景
## 范围（按域分节 A/B/C...，每节含 Schema 变更、接口契约、页面行为等具体口径）
## Testing Decisions
- 好测试只测外部行为（接口返回形态/页面可见结果/消息到达），不测内部实现
- 断言接缝：列出用哪些既有演练脚本体系扩展、是否新增接缝（WS/视觉族）
- 回归红线：哪些既有断言/行为不得回退
- 测试数据：种子与造数口径
## Out of Scope（显式列出不做的事，防蔓延）
## Further Notes
- 需求方确认记录（Q1~QN 逐题拍板结果与日期）
- 术语（有领域术语表时对齐）
```

**Testing Decisions 必须先于工单拆分写好**——测试接缝决定验收形态，验收形态决定工单边界。

### 3. 工单拆分

拆分原则（粒度锚点来自实战）：

1. **可独立验收**：每张票有明确 DoD 与可执行的验收标准（能落成 api-rehearsal 断言或 shot-* 视觉屏的才算合格；测不了的验收标准回炉重写）；
2. **粒度适中**：单仓一张票 ≈ 一轮实施可完成（≤10 个文件级改动参照）；天然跨域的大票显式标"双仓/多仓"；
3. **依赖显式**：`Blocked by: NN` / `协调：与 NN 同改 <文件>` 两类标注都写；串行链给建议合入顺序；
4. **正交不重叠**：两张票不改同一区块；确需同文件时用"协调"标注并给先后序；
5. 上游先行：权限/枚举/schema 类基座票排前，UI/消费方票排后；独立小票（安全补齐/杂项）可插空。

每张工单 `.scratch/<feature>/issues/NN-<slug>.md`：

```markdown
# NN <标题>（一句话说清做什么）
Status: needs-triage
Spec: .scratch/<feature>/spec.md（<对应节>）

## 目标
## 范围（逐条，含实现口径的关键决策）
## 验收（可执行化：断言清单/视觉屏清单/回归红线）
## 依赖
Blocked by: <NN 或 无>
## Comments
```

### 4. 拆分确认（拍板点二）

1. 输出**拆分摘要表**给用户：`| # | 标题 | 粒度（单仓/双仓） | 验收形态 | 依赖 |` + 建议派工顺序；
2. 用户逐张或整体确认后：把首张可派工单 `Status:` 置 `ready-for-agent`，其余按依赖保持 `needs-triage`（前置完成后由 duo-dispatch/review 解锁时翻转）；
3. 提示下一步：`/duo-dispatch NN` 派首张。

## 边界

- 拆分只产出 spec 与工单文件，**不写任何业务代码**；
- 需求信息不足以写出可执行验收标准的部分，进 spec 的 Out of Scope 或单列"需求缺口"小节待补，不硬拆；
- 用户只想要 spec 不想拆单（或反之）：按需执行对应步骤，流程可裁剪；
- 已有 spec 的增量需求：读现有 spec 与工单状态，走"追加范围节 + 新工单续号"路径，不重写历史。
